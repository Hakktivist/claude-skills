# Manual Review

## Overview

Produces a scan list of the files you changed, ordered bottom-up through the stack — schema/data layer first, then backend logic, then the API/interface layer, then frontend/UI — so a reviewer builds context before hitting the surface they actually care about. One line per file: what changed, or what it's for if new. Not a narrative summary.

## Scope

Default to the current diff: `git status --porcelain` (uncommitted) plus, if the branch has commits ahead of the base branch, `git diff --name-only $(git merge-base <base> HEAD)...HEAD`. Use a different range or file set only if the user specifies one.

## Ordering

Bucket every file by the layer it lives in. Layers are project-agnostic — infer them from the actual project structure (check CLAUDE.md/AGENTS.md, or just look at directory/file naming conventions), but the usual bottom-up order is:

1. Schema/migrations — DB schema files, migration folders
2. Data/auth layer — repositories, data-access modules, ORM models, authorization/store descriptors
3. Business logic — services, domain logic, use-cases
4. API/interface layer — routers, controllers, API routes, GraphQL resolvers
5. Frontend/UI — components, pages, views, templates
6. Tests — grouped with the layer they cover if that reads better than a trailing bucket
7. Everything else — config, docs, scripts, tooling

Don't re-derive order from the import graph — bucket by what the file obviously is and keep buckets in the order above. It's a fast, repeatable heuristic, not a dependency analysis. Omit empty buckets. Within a bucket, order by likely reading order (e.g. a types/constants file before the file that consumes it), or fall back to alphabetical.

## Writing the one-liner

Read the actual diff per file — `git diff -- <path>` for uncommitted, `git diff <base>...HEAD -- <path>` for committed — don't guess from the filename. State the specific change and why it matters to a reviewer ("adds X check", "new method Y", "wires Z into the state machine"), not "updated file". For a new file (`??` in git status, or no `-` lines in the diff), describe its purpose instead.

If a generated/autogenerated file picked up unrelated regeneration drift alongside the intended change, say so explicitly rather than silently listing it as if it were reviewed content.

## Output format

Group by layer with a header, numbered within each group, no commentary beyond the one-liner:

```
## Schema
1. `prisma/schema.prisma` — adds `churn_escalation_count` to `role_churn_risk_state`

## Data/auth layer
2. `lib/repositories/role_churn_risk_state.repository.ts` — new `enterParkedMonitoring()` method, idempotent against overlapping cron runs

## Business logic
3. `lib/services/churn_risk/churn_risk.service.ts` — routes capped re-entries into parking instead of Needs Action

## API/interface layer
4. `server/api/routers/churn-risk.ts` — plumbs `isParked` from service to tRPC output
5. `server/api/routers/churn-risk.outputs.ts` — regenerated sister file for the new field

## Frontend
6. `components_new/paratools/pararoles/RolesKanbanCard.tsx` — shows a "Parked" pill on capped roles
```
